## 总体规划

### 2026-07 本地单机执行方案更新

导师已分配 Ubuntu 单机服务器用于 SWE-bench Pro 评测，后续停止云端部署脚本开发，主实验改为本地 Docker 单机并发：

- 执行入口：`python eval/local_swebench_runner.py --manifest <manifest.json>`。
- 输入：本地 manifest JSON，包含 `models` 与 `issues`，runner 展开为 `(model, issue)` 任务。
- 输出：每个任务直接写入 `workdir/swe_issue_NNN/<output_subdir>/`，包括 `patch.diff`、`prediction.json`、`run_metrics.json`、`eval_result/`、`logs/` 和 `runner_task.json`。
- 并发：32GB 内存默认按 `per_task_gb=6`、`reserve_gb=6`、`hard_cap_workers=4` 估算，默认约 4 路；若 OOM 则降到 2 路或提高单任务内存预算。
- 磁盘：每个 `(model, issue)` 完成后立即 `docker rm -f` 容器、`docker rmi -f` 相关镜像，并默认执行 `docker image prune -a -f`，避免 400GB 磁盘被历史 issue 镜像占满。
- 续传：已完成且已有 `eval_result/eval_summary.json` 的 output_subdir 自动跳过；存在 `checkpoint.json` 的 output_subdir 交给 `src.main` 继续恢复；只缺评测结果时使用 `--redo-eval` 补跑。

manifest 示例：

```json
{
  "models": [
    {
      "name": "claude-sonnet-4.5",
      "backend": "anthropic",
      "env": {
        "ANTHROPIC_MODEL": "claude-sonnet-4.5"
      },
      "output_subdir": "outputs_claude-sonnet-4.5"
    }
  ],
  "issues": ["001", "002", "003"],
  "max_workers": 4
}
```

GPT 模型使用新中转时，manifest 中显式设置 OpenAI 后端：

```json
{
  "models": [
    {
      "name": "gpt-5.2",
      "backend": "openai",
      "env": {
        "MODEL_BACKEND": "openai",
        "OPENAI_BASE_URL": "https://claude.buzz7.top/",
        "OPENAI_MODEL": "gpt-5.2",
        "OPENAI_API_SURFACE": "responses"
      },
      "output_subdir": "outputs_gpt-5.2"
    }
  ],
  "issues": ["001"],
  "max_workers": 2
}
```

密钥只放在服务器 `.env` 或进程环境变量 `OPENAI_API_KEY` 中，不写入 manifest。BUZZ 官方文档说明 OpenAI SDK 只需配置 `base_url` 和 `api_key`，并通过 `/v1` 的 OpenAI-compatible 端点转发请求；当前 `https://claude.buzz7.top` 对 `gpt-5.2` 实测要求走 `/v1/responses`，因此 manifest 使用 `OPENAI_API_SURFACE=responses`。2026-07-04 本地 SDK 探活已通过：`gpt-5.2` 返回 `pong`。

**RQ1: How effective is our approach in resolving repository-level bugs compared with state-of-the-art SWE agents?**
 **数据来源：**主实验。
 **需要展示：**
 1.pass@1 / resolved rate、fail2pass, pass2pass等最终结果
 2.跟其他baseline对比
**预期结论：**我们的方案有效性优于SOTA agent

**RQ2: How does evidence-closure-aware control improve the agent’s patch commitment behavior?**
 **数据来源：**主实验、消融实验。
 **需要展示：**
1.一个case study（SOTA解决失败，我们解决成功）
 2.主实验的过程间数据：比如四类证据的数量、质量（通过ground-truth来人工标签，比如bug症状、定位是否准确）、闭环检查情况（生成patch的时候闭环检查是否成功、迭代的次数）。
 3.四个消融组的过程间数据
**需要分析：**
1.用case study进行拆解分析，SOTA解决失败的，我们如何通过搜集证据闭环成功解决
 2.主实验的过程间数据经过标注 -> 高质量的四类证据 -> 最终效果好
 3.对比消融组 -> 四类证据在质量上出现下降 -> 最终效果下降
**预期结论：**
 1.insight的正确性：四类证据的数量和质量是影响agent修复效果的关键因素。
 2.方案各个组件对于搜集高质量闭环证据的有效性

## 要统计的指标和交付形式
### 总览
 1)pass率（pass@1, fail2pass, pass2pass）
 2)每一个case的开销（时间、token）
 3)证据搜集和闭环检查的一些过程数据。

### 过程数据指标
- RequirementItem 总数
- 各 verdict 分布（AS_IS_VIOLATED / TO_BE_MISSING / COMPLIANT）
- Grounding Accuracy（Precision / Recall / HitFile，对照 gold patch）
- rework 轮次分布 + CLOSURE_FORCED_FAIL 比例（原"rework 轮次"与"闭环强制失败次数"合并）
- repatch 轮次 + build gate 通过/失败分布
- 最终patch状态分布（PATCH_SUCCESS / BUILD_FAILED / EVIDENCE_INCOMPLETE）
- 证据积累斜率（随 deep search rounds 增加，各证据卡片条目数的积累曲线，与最终 pass 率联合分布）
**注意：Grounding Accuracy需要人工标注，只有消融组里的case需要这个值**

### 开销指标
- Token / Cost：每个任务的 Token 输入/输出开销
- Wall-clock time：每个任务完成的时间戳
- LLM Invocations：deep search + closure check + patch 调用次数，原 Average Turns 改名
- 工具调用次数：Grep/Read/Glob 等调用总数
- deep search 轮次

### 泛化性指标
- Resolved rate by language
- Resolved rate by repo
- Evidence Count by Edited Files（按 patch 复杂度分层的证据数分布）（初步认为分类为：Edited Files为1-2、3-4、5-6、7-10、10+）

你统计结果的时候需要产出2类csv，一类是最后的统计数字。另外一类csv是详细记录的每个case的具体情况（消融组中的case要另外标记）。
做实验的时候记得留意我们每个RQ的设置和分析项，不要漏掉一些数据或者方向跑偏。



## 失败分析
记录的指标要能支撑两件事：自动分类失败类型，以及定位每类失败的根因。
在 731个 case 跑完后写一个后处理脚本，对每个 unresolved case 输出一个failure_diagnosis.json，字段包含下述所有指标 + 自动归入的 Type A/B/C/D，方便后续统计和 case study 挑选。

#### 第一层：失败类型判定（自动）
每个 unresolved case 先按以下优先级归入一类：
1. **Type A（定位完全偏离）：** `HitFile = 0`
    *↓ 如果不是，则判断下一项*
2. **Type B（闭环耗尽）：** `patch_result = EVIDENCE_INCOMPLETE`
    *↓ 如果不是，则判断下一项*
3. **Type C（patch 编译/结构错误）：** `patch_result = BUILD_FAILED`
    *↓ 如果不是，则判断下一项*
4. **Type D（定位方向对但修复逻辑错）：** `patch_result = PATCH_SUCCESS` but SWE-bench unresolved
这四类构成互斥的失败分类，Type A 优先级最高（连文件都没找到，后面的信息都不可信）。

#### 第二层：每类失败的诊断指标
Type A — 定位完全偏离（HitFile = 0）
| **指标** | **来源** | **用途** |
| --- | --- | --- |
| deep search 轮次 | action_history | 是轮次不够还是搜索方向错了 |
| 最终 verdict 分布 | evidence.json | 是否所有 req 都到了 UNCHECKED/无 evidence_location |
| CLOSURE_FORCED_FAIL 是否触发 | patch_outcome.json | 区分“找不到→强制结束”和“找错了→closure 通过” |
| 语言 / repo | instance metadata | 是否集中在某语言（支撑 RQ4） |

Type B — 证据闭环耗尽（EVIDENCE_INCOMPLETE）
| **指标** | **来源** | **用途** |
| --- | --- | --- |
| 闭环失败的 dimension（Sufficiency / Consistency） | patch_outcome.json 或 closure checker 输出 | 是证据不足还是内部矛盾 |
| 哪些 req 反复 rework（req id + rework 次数） | action_history | 定位是哪类 requirement 最难闭环 |
| rework_context 内容摘要 | evidence.json 的 rework_context 字段 | closure checker 给的反馈是否有规律 |

Type C — BUILD_FAILED
| **指标** | **来源** | **用途** |
| --- | --- | --- |
| 触发的具体 gate（go vet / pytest collect / rename_residue / contract_drift 等） | build_verification.json | 区分是语言编译问题还是结构一致性问题 |
| 错误是否跨 repatch 轮次持续（同一错误出现几轮） | build_verification.json 多轮对比 | patch planner 是否在原地循环 |
| 最终 repatch 轮次 | build_verification.json | 是否因轮次耗尽而放弃 |
| gold patch 修改文件数 | SWE-bench instance metadata | 复杂 case 更容易 BUILD_FAILED |

Type D — 定位方向对但逻辑错（PATCH_SUCCESS + unresolved）
| **指标** | **来源** | **用途** |
| --- | --- | --- |
| Grounding Precision / Recall | 对照 gold patch 计算 | 区分“文件对但行错”和“行也基本对但修复逻辑错” |
| patch plan 的 file coverage vs gold patch files | patch_plan.json vs gold patch | 是否漏了某些文件 |
| AS_IS_VIOLATED req 数 vs gold patch 实际改动范围 | evidence.json + gold patch | 需求分析是否遗漏了某个修改点 |
| 是否触发 check_plan_covers_violations 拦截 | action_history | 如果触发了但仍然 unresolved，说明 re-plan 没有修正问题 |
具体来说，unresolved case 里的 `fail2pass` / `pass2pass` 可以进一步拆分 Type D：
| **fail2pass** | **pass2pass** | **含义** |
| --- | --- | --- |
| = 0 | 不变 | patch 完全没有正向作用，方向完全错 |
| > 0，但不够 | 不变 | 部分修复，定位对了但 fix 不完整（最有价值的 case study 来源） |
| > 0 | 下降 | 修了一部分但引入了回归，patch 有副作用 |
| = 0 | 下降 | patch 只破坏了原有功能，完全错误方向 |
这样 Type D 就能细分为 **D1（部分修复）**、**D2（修复+回归）**、**D3（无效）**、**D4（纯回归）** 四个子类，失败原因更清晰。
另外，`pass2pass` 对 Type C也有参考价值，如果 build gate 挡住了 patch，但 `pass2pass` 在之前的 repatch 轮里已经出现下降，说明 patch planner 在错误方向上越改越远，而不只是语法问题。

#### 第三层：所有失败 case 的共同 metadata
无论哪类失败，都需要这些字段来支撑分布分析和 case study 选取：
| **指标** | **说明** |
| --- | --- |
| 编程语言 | 支撑 RQ4 交叉分析 |
| gold patch 修改文件数 / 行数 | 复杂度代理变量 |
| RequirementItem 总数 | 任务规模 |
| token 消耗 | 排查是否因 budget 不足导致失败 |
| 是否有 dynamic grounding unverifiable | 区分工具链缺失导致的失败 |
