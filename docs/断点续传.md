# 断点续传指南

## 2026-07 本地单机 runner 更新

新的执行入口是 `eval/local_swebench_runner.py`，不再开发或依赖云端部署脚本。它读取本地 manifest JSON，把任务展开为 `(model, issue)`，并把每个任务的 patch、SWE-bench Pro 评测结果、日志和状态写回本地：

```bash
python eval/local_swebench_runner.py \
  --manifest manifests/swebench_pro_local.json \
  --max-workers 4
```

推荐 manifest 结构：

```json
{
  "models": [
    {
      "name": "claude-sonnet-4.5",
      "backend": "anthropic",
      "env": {
        "ANTHROPIC_MODEL": "claude-sonnet-4.5"
      },
      "output_subdir": "outputs_claude-sonnet-4.5"
    }
  ],
  "issues": ["001", "002", "swe_issue_003"],
  "max_workers": 4
}
```

GPT 模型的新中转配置使用 OpenAI-compatible 后端：

```json
{
  "name": "gpt-5.2",
  "backend": "openai",
  "env": {
    "MODEL_BACKEND": "openai",
    "OPENAI_BASE_URL": "https://claude.buzz7.top/",
    "OPENAI_MODEL": "gpt-5.2",
    "OPENAI_API_SURFACE": "responses"
  },
  "output_subdir": "outputs_gpt-5.2"
}
```

`OPENAI_API_KEY` 放在服务器 `.env` 或进程环境变量里，不写入 manifest。`src.agents._openai_native` 会自动把 `OPENAI_BASE_URL=https://claude.buzz7.top/` 规范化为 `/v1`。当前 buzz7 对 `gpt-5.2` 要求走 `/v1/responses`，所以必须设置 `OPENAI_API_SURFACE=responses`。

每个任务的主要输出目录为：

```text
workdir/swe_issue_NNN/<output_subdir>/
├── patch.diff
├── prediction.json
├── run_metrics.json
├── runner_task.json
├── eval_result/
│   ├── eval_results.json
│   └── eval_summary.json
└── logs/
    ├── generate.log
    ├── eval.log
    └── docker_cleanup.log
```

续传规则：

- 如果 `<output_subdir>/checkpoint.json` 存在，runner 不跳过该任务，而是再次调用 `src.main`，由 harness 从 checkpoint 恢复。
- 如果 `<output_subdir>/eval_result/eval_summary.json` 或 `runner_task.json(status=success)` 已存在，runner 默认跳过该 `(model, issue)`。
- 如果只生成了 patch 但没有评测结果，可使用 `--redo-eval` 继续补评测。
- 如果明确要从头重跑，使用 `--force-restart`，它会把该参数传给 `src.main` 并绕过跳过逻辑。

并发规则：

- 默认按内存估算并发：`floor((MemTotal - reserve_gb) / per_task_gb)`，再受 CPU 和 `--hard-cap-workers` 限制。
- 32GB 机器的默认值是 `--per-task-gb 6 --reserve-gb 6 --hard-cap-workers 4`，通常得到 4 路并发。
- 如果出现 exit 137/OOM，先降到 `--max-workers 2` 或把 `--per-task-gb` 提高到 `8`。

磁盘回收规则：

- 每个 `(model, issue)` 完成后，无论成功失败，都会立即执行确定性容器名的 `docker rm -f`。
- runner 会对本任务实际使用的镜像执行 `docker rmi -f <image>`。
- 默认还会执行 `docker image prune -a -f` 和 `docker container prune -f`；只有显式传 `--no-prune` 才会关闭。
- 为避免并发 prune 误删刚 pull 但尚未 create 的镜像，runner 把 `docker pull + docker create` 放在同一把进程内 Docker 锁里；容器创建后镜像被容器引用，prune 不会删除正在使用的镜像。

## 概述

harness 每完成一个关键节点就自动将完整运行状态存档到 `checkpoint.json`，下次启动时自动检测并从断点恢复，无需人工干预。

---

## 工作原理

### checkpoint 保存时机

| 触发时机 | checkpoint 保存的状态 | 说明 |
|---------|-------------------|------|
| 每轮 deep-search 完成后 | `UNDER_SPECIFIED` | 最常见的保存点；每轮证据搜集完成即落盘 |
| closure checker 通过后 | `CLOSED` | 所有证据已通过审核，下次从 patch 规划阶段续跑 |

### 保存内容

`workdir/<issue_name>/outputs_<model>/checkpoint.json` 包含：
- 当前 `PipelineState`（状态名）
- 完整的 `SharedWorkingMemory`（证据卡、patch 计划、LTM 块等全部字段）
- 预算计数器（已用 deep-search 轮次、rework 轮次、repatch 轮次等）

### 自动清理

当 pipeline 到达任何终端状态（`PATCH_SUCCESS` / `PATCH_FAILED` / `CLOSURE_FORCED_FAIL`），`checkpoint.json` 会在所有输出文件写完后自动删除。正常完成的 case 不会留下 checkpoint 文件。

## 使用方法

### 正常运行（自动续跑）

重新用相同命令启动即可，harness 会自动检测 `checkpoint.json`：

```bash
# 主机模式
python -m src.main --instance-json workdir/swe_issue_001/artifacts/instance_metadata.json \
    --repo-dir workdir/swe_issue_001/repo

# Docker 模式（run_docker_issues.ps1 内部调用，无需手动）
.\eval\docker\run_docker_issues.ps1 -Only 001
```

如果存在 checkpoint，输出会显示：
```
[resume] Checkpoint found (state=UNDER_SPECIFIED, saved=2026-07-02T10:30:00Z). Resuming from last save point.
[resume] Restoring pipeline at state=UNDER_SPECIFIED (checkpoint saved 2026-07-02T10:30:00Z)
```

### 强制从头重跑（忽略 checkpoint）

```bash
python -m src.main --instance-json workdir/swe_issue_001/artifacts/instance_metadata.json \
    --repo-dir workdir/swe_issue_001/repo \
    --force-restart
```

输出会显示：
```
[resume] --force-restart: ignoring existing checkpoint, starting fresh.
```

## 典型场景

### 场景 1：网络中断导致 deep-search 中止

运行 3 轮 deep-search 后网络中断：
- checkpoint 已在第 3 轮完成后自动保存
- 重新启动命令 → 自动从第 4 轮 deep-search 开始续跑
- 前 3 轮的证据完整保留，不重复调用 LLM

### 场景 2：手动中断后想换时间段继续

用 Ctrl+C 中断正在运行的 case：
- 若中断发生在某一轮完成之后，checkpoint 已保存
- 任意时间重新运行同一命令即可续跑

### 场景 3：closure 已通过，想重新生成 patch

closure 批准后 checkpoint 保存为 `CLOSED` 状态：
- 删除现有 `patch.diff`（可选）
- 重新运行命令 → 自动从 patch 规划阶段开始，跳过所有证据收集

### 场景 4：明确要从头重来

```bash
python -m src.main ... --force-restart
```

或手动删除 checkpoint 文件：
```powershell
Remove-Item workdir\swe_issue_001\outputs_gpt-5.2\checkpoint.json
```

## 恢复点说明

| 恢复状态 | 跳过的工作 | 重新执行的工作 |
|---------|-----------|--------------|
| `UNDER_SPECIFIED` | 已完成的 deep-search 轮次（从 checkpoint 恢复证据） | 剩余 deep-search 轮次 → closure → patch |
| `CLOSED` | 全部 deep-search + closure 过程 | LTM 检索 → patch 规划 → patch 生成 → build 验证 |

**注意**：恢复至 `CLOSED` 状态时，harness 会重新运行 patch planner（约 2-3 分钟），因为本地 patch 计划无法保证 repo 状态与上次完全一致。

## 注意事项

1. **checkpoint 与模型/代码版本绑定**：如果更换了模型（如改 `.env` 里的 `ANTHROPIC_MODEL`）或修改了 evidence 数据模型，旧 checkpoint 可能不兼容。此时用 `--force-restart` 从头开始。

2. **Docker 模式**：`run_docker_issues.ps1` 会在每个 case 结束后自动删除容器。如果容器被意外 kill（exit 137 OOM），checkpoint 文件留在 `workdir/swe_issue_NNN/outputs_<model>/` 中，下次再次运行同一 issue 号时会自动续跑。

3. **并发安全**：不要同时对同一 issue 启动两个 harness 进程——两者会争写同一 `checkpoint.json` 和 `evidence.json`。
