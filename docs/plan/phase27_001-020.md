## 运行中修复的问题

1. Docker 反向代理隧道

   Paramiko 反向转发在大镜像层下载时不稳定，Docker pull 会报：

   ```text
   proxyconnect tcp: dial tcp 127.0.0.1:7897: connect: connection refused
   ```

   改用 OpenSSH：

   ```bash
   ssh -N -T -R 7897:127.0.0.1:7897 user@172.28.8.77
   ```

2. Generation container entrypoint

   ansible 镜像默认 entrypoint 不接受 `-c`，导致：

   ```text
   exec: "-c": executable file not found in $PATH
   ```

   runner 需要对 generation container 显式传 `--entrypoint /bin/bash`。

3. Secret 日志脱敏

   初版 runner 会把 `docker create -e OPENAI_API_KEY=...` 原样写入 `generate.log`。已修复为写日志前替换为 `<redacted>`，并清洗旧日志。最终扫描 `secret_hits 0`。

4. Eval workspace 权限

   本地 Docker eval 会生成 root-owned `output.json/stdout.log/stderr.log`。`collect_outputs_local()` 复制 workspace 文件到同一路径时触发 `PermissionError(13)`。已修复为 src/dst 相同时跳过复制，并对已有输出目录 chown。

## 失败 Case 暴露的通用 Harness 问题

这些问题不是某个 case 的特例，而是 harness 设计层面的共性短板，可以通过小幅改造改善。

### 1. Build/Verify 不应依赖宿主机 Toolchain

多个 Go case 的 `build_verification.json` 显示：

```text
FileNotFoundError: [Errno 2] No such file or directory: 'go'
```

这说明 patch 生成阶段的 build gate 在宿主环境或不完整环境中运行，而不是在 SWE-bench case 镜像内运行。Go case 因此经常被标记为 `BUILD_UNVERIFIABLE` 或带着弱信号进入 eval。

建议：build/verify 命令也放进 case Docker image 的 `/app` 中运行，复用 evaluator 的镜像、环境和依赖。

### 2. Node/JS Build Gate 太弱

NodeBB case 出现 `skipped_build: true`，但最终 eval 差 1 个测试或大量测试未过。跳过 build 让 harness 只能靠静态判断和 closure 检查，无法提前捕捉路由、集成、测试引用等问题。

建议为 JS/Node 增加轻量验证策略：

- package script 探测。
- 目标文件 import/require 检查。
- 可用时运行 lint、tsc、npm test dry-run 或目标测试 discovery。
- 不要直接 `skipped_build`。

### 3. Patch Outcome 语义不准确

本次有 `PATCH_FAILED` 但 SWE-bench resolved 的 case，也有 `PARTIAL_PATCH` 但 unresolved 的 case。这说明当前 `patch_outcome` 不是准确的最终补丁质量标签，而是混合了 build gate、closure、patch application、best-effort fallback 等内部过程信号。

主实验指标只看 pass@1：

```text
swebench_resolved / resolved
```

过程诊断字段应拆开：

```text
harness_patch_outcome
build_gate_outcome
swebench_resolved
eval_fail_to_pass_delta
```

建议后续把 `PATCH_FAILED` 拆细，例如：

```text
PATCH_APPLY_FAILED
BUILD_GATE_FAILED
CLOSURE_FORCED_FAIL_BEST_EFFORT
PATCH_GENERATED_WITH_WARNINGS
```

避免一个状态覆盖多种含义。

### 4. 需求拆解过细，Closure 阶段容易耗尽预算

日志中多次出现 deep-search 到 20-30 轮、closure forced fail 或 degraded patch。很多要求是同一行为的路径、函数、输入输出拆分，导致 harness 把时间花在证明细粒度 requirement，而不是快速形成可验证补丁。

建议微调需求合并策略：

- 按行为目标合并相邻 requirement。
- 把 path/type/input/output、文件位置、接口签名等 metadata 降级为 evidence hint。
- metadata 不作为独立必须闭合的 requirement。

closure 预算可以按 requirement 数量动态调整，但要控制上限：

```text
budget = min(max_rounds, base_rounds + weighted_requirement_count)
```

其中 `weighted_requirement_count` 只统计行为性 requirement；metadata 低权重或不计入。

还应增加停滞保护：如果连续多轮只在同一 requirement 上 rework 且没有新增 evidence，就提前降级为 best-effort patch。

### 5. 动态 Grounding 结构化输出需要降级策略

运行中出现过 OpenAI structured output validation retry，例如 `backend` 返回空字符串。当前会重试，但仍会消耗预算。

建议对动态 grounding 的 schema 增加宽容解析：

- 非法 enum 时落到 `synthetic_script` 或 `unverifiable`。
- 原始响应记录为 warning。
- 不阻断主流程。

### 6. Docker 文件所有权要作为 Runner 契约处理

本地 Docker eval 会产生 root-owned 文件。runner 必须在每个容器结束后统一执行 ownership normalization，或在容器内用宿主 UID/GID 运行。否则会出现非 case 级 `PermissionError(13)`，影响所有 case 的评测收尾。

## 明确不做

不做 eval 后重修。

正式实验记录 pass@1。生成 patch 后只做一次 SWE-bench eval；eval 输出只用于统计和事后诊断，不进入同一次提交的修复闭环。

## 建议优先级

优先改：

1. build/verify 全部进 case Docker image。
2. eval workspace chown 或 same-path copy guard 固化。
3. secret 日志脱敏固化。
4. metrics 增加 eval delta 和失败测试摘要。
5. requirement 合并和动态 closure 预算策略。

其次改：

1. JS/Node 轻量 build gate。
2. dynamic grounding 宽容解析。
